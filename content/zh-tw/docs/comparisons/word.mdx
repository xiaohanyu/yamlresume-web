---
title: YAMLResume 與 Microsoft Word 的比較
---

[Microsoft Word](https://www.microsoft.com/en-us/microsoft-365/word)
是全世界大多數人撰寫履歷的方式。它是求職申請的預設格式，安裝在數億台電
腦上，其模板圖庫提供數千種設計。如果招募人員請您「把履歷傳過來」，十之八
九他們期待的是 `.docx` 檔，或是從 Word 匯出的 PDF。

摘自 Microsoft 官方的產品頁面：

```markdown
- Word works across devices—on desktop (Windows and macOS), mobile, tablets
  (iOS and Android) or online.
- Word for the web is free for anyone to use online.
- Real-time collaboration means fewer email attachments and faster feedback.
```

重點在於：**選擇 YAMLResume 並不代表放棄與 Word 相容的輸出。** YAMLResume
具備專用的 [DOCX 引擎](/zh-tw/docs/layouts/docx)，只要一道指令就能從您的
YAML 原始碼建置 Microsoft Word 文件。真正的比較並不是「YAML 對上
`.docx`」——而是**手動編輯文件對上編譯式的結構化輸出**。這個差異涉及版本
控制、驗證、一致性、多格式發佈，以及自動化。

以下為兩種工作流程的比較：

## 功能比較

| 功能             | YAMLResume                                                                                                                                        | Microsoft Word                         |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| **類型**         | 履歷編譯器（CLI 工具鏈）                                                                                                                                    | 通用文書處理器                                |
| **撰寫格式**       | 純文字 YAML                                                                                                                                          | 二進位 `.docx`（一個裝滿 XML 的 ZIP 壓縮檔）        |
| **格式設定**       | 由模板產生，格式保持一致                                                                                                                                      | 手動——樣式、定位點與間距會隨時間漂移                    |
| **結構驗證**       | [嚴格的 Zod 驗證](/zh-tw/docs/compiler/schema)，搭配 [clang 風格的診斷訊息](/zh-tw/blog/yamlresume-compiler)                                                     | 結構方面無驗證——只有拼字與文法檢查                     |
| **輸出格式**       | [DOCX](/zh-tw/docs/layouts/docx)、[HTML](/zh-tw/docs/layouts/html)、[Markdown](/zh-tw/docs/layouts/markdown)、[LaTeX/PDF](/zh-tw/docs/layouts/latex) | `.docx`、PDF（透過另存新檔），以及其他格式的有損匯出        |
| **DOCX 輸出**    | 內建 [DOCX 引擎](/zh-tw/docs/layouts/docx)，附精選模板                                                                                                      | 文件本身就是 DOCX                            |
| **模板**         | 精選的官方模板集（DOCX 使用 `calm`；[LaTeX](/zh-tw/docs/layouts/latex/templates) 與 [HTML](/zh-tw/docs/layouts/html/templates) 有更多）                            | 透過 Microsoft Create 與第三方提供數千個模板；品質參差不齊 |
| **版本控制**       | 可搭配 Git；差異比對會顯示真正的變更                                                                                                                              | 二進位檔案——差異比對與合併幾乎無用                     |
| **客製化**        | 每份申請使用各自的版面配置檔與 Git 分支                                                                                                                            | 「另存新檔」的副本彼此漂移（`resume_final_v2.docx`）  |
| **國際化**        | [10 種語言橫跨 12 個語系代碼](/zh-tw/docs/locale)，加上 [AI 翻譯](/zh-tw/docs/ai/translate)                                                                      | 多語言的 UI 與拼字檢查；每種語言都是一份獨立的手動文件          |
| **富文字**        | 在 `summary` 欄位中使用精選的 [Markdown 語法](/zh-tw/docs/content/rich-text)                                                                                 | 任何地方都有完整的格式設定                          |
| **資料模型**       | 固定、結構化的結構描述；具備 [JSON Resume](/zh-tw/docs/comparisons/json-resume) 互操作性                                                                            | 自由格式文件                                 |
| **AI 功能**      | CLI 內建的[產生](/zh-tw/docs/ai/generate)與[翻譯](/zh-tw/docs/ai/translate)功能                                                                             | Microsoft 365 Copilot 功能（需訂閱）          |
| **協作**         | 在純文字上進行 Git 拉取請求與程式碼審查                                                                                                                            | 優秀的即時共同編寫、註解與追蹤修訂                      |
| **ATS 相容性**    | 乾淨、由結構化資料產生的文件結構；文字欄位可輸出 [Markdown](/zh-tw/docs/layouts/markdown)                                                                                 | 取決於模板紀律——表格、文字方塊與欄位會讓許多解析器失效           |
| **確定性輸出**      | 是——相同輸入，在任何機器上都產生相同的位元組                                                                                                                           | 字型與版面會在不同機器與 Word 版本之間漂移               |
| **開發模式**       | [`yamlresume dev`](/zh-tw/blog/dev-mode) 會在每次儲存時重新建置                                                                                              | 所見即所得（WYSIWYG）編輯（即時，但手動）               |
| **CI/CD 與自動化** | [GitHub Action](https://github.com/yamlresume/action)、[Docker](/zh-tw/docs/contributing/docker)、[`@yamlresume/node`](/zh-tw/docs/ecosystem/node)  | 沒有內建的履歷功能                              |
| **離線**         | 是，安裝之後即可                                                                                                                                          | 桌面版應用程式可以；Word 網頁版需要網路連線               |
| **成本**         | 免費（開源）                                                                                                                                            | Microsoft 365 訂閱；功能有限的免費網頁版            |

## 主要差異說明

### 手動格式設定對上自動產生的格式設定

在 Word 中，格式設定是您的責任。每個項目符號的縮排、每個日期的定位點，
以及每個粗體職稱，都是您要做、而且要不斷重複做的決定。經過數個月的編輯，
文件會漂移：間距變得不一致、新項目用了略有不同的符號，而「改一個小地方」
要花上二十分鐘的微調。研究顯示，大多數 Word 使用者從未使用命名樣式，因此
格式最後變成一次性的手動調整，日後修改非常痛苦。

在 YAMLResume 中，格式設定是編譯器的工作。您的內容是資料；[DOCX 引
擎](/zh-tw/docs/layouts/docx)與 [LaTeX 引擎](/zh-tw/docs/layouts/latex)會透過
強制一致性的模板來渲染它。在一個地方修改您的職稱，下一次建置時每種格式
——DOCX、PDF、HTML、Markdown——都會自動跟上。模板把每個設計決策做一次，
而且一次就做對。

### 純文字對上二進位

`.docx` 檔案是一個裝滿 XML 的 ZIP 壓縮檔。Git 無法以有用的方式對它做差異
比對、合併履歷的兩個版本意味著手動複製貼上，而「三月到六月之間改了什麼？
」意味著開啟兩個檔案並排比較。這就是為什麼 Word 履歷會堆積成
`Resume.docx`、`Resume_new.docx`、`Resume_newer.docx`、
`Resume_FINAL_tracked.docx`，塞在一個沒人敢清理的資料夾裡。

YAMLResume 檔案是純文字。`git diff` 會準確顯示變更內容：

```diff
-    position: Senior Software Engineer
+    position: Staff Software Engineer
     startDate: Jan 2020
-    endDate: Dec 2024
+    endDate:
```

純文字開啟了所有常見的開發者工具：每個職缺申請一個分支、對自己的職涯歷程
進行拉取請求審查、CI 中的自動建置，以及一份永久且可搜尋的歷代履歷檔案。

### 驗證：拼字檢查不等於結構檢查

Word 會為拼錯的雇主名稱畫上底線，但它會讓您儲存結束日期早於開始日期、電
子郵件缺少 `@`，或城市欄位只有一個字母的履歷。這些都不是拼字錯誤，所以它
們都不會被標記。

YAMLResume 會在渲染任何內容之前先驗證結構。[編譯器](/zh-tw/docs/compiler/architecture)
會根據嚴格的 Zod 結構描述檢查您的履歷，並回報附帶行號與原始碼片段的
[clang 風格診斷訊息](/zh-tw/blog/yamlresume-compiler)，讓錯誤在您撰寫時就被
攔下，而不是等到招募人員發現。

### 客製化調整，免於副本混亂

職涯建議說得很清楚：為每份申請客製化您的履歷。在 Word 中，這通常意味著選
擇「另存新檔」並編輯副本。但副本很快就會失去同步——修正其中一個檔案的錯
字、忘了另一個，現在您有兩份不同的履歷，卻不知道哪份才是對的。

在 YAMLResume 中，您的內容檔案保持為單一真實來源。客製化調整發生在版面
配置檔中：[章節別名與排序](/zh-tw/docs/layouts/sections/aliases)可以依變體而
變，而 Git 會把它們與您的內容放在一起追蹤。十個客製化變體，只是十個指向同
一份履歷的小型版面配置檔——而不是十份彼此漂移的獨立文件。

### 國際化：公平地說

Word 在這方面表現出色：它能很好地處理多語言文件、拼字檢查與複雜文字——包
括中文、日文與韓文——而且在許多非英語國家，它是製作履歷的標準工具。如果
您只用一種語言撰寫一份履歷，Word 的多語言支援就不是您的問題。

當同一份職涯必須說多種語言時，YAMLResume 就展現出優勢。設定 `locale` 鍵
會翻譯章節標題、學位、技能等級與國家名稱；以本地慣用格式呈現日期與地址；
並套用橫跨 [10 種語言與 12 個語系代碼](/zh-tw/docs/locale)的語系標點規則。
搭配 [`yamlresume ai translate`](/zh-tw/docs/ai/translate)，英譯日的變體只
需要一道指令，而且因為是從相同來源產生，兩者永遠不會漂移。在 Word 中，這
意味著兩份文件和一位翻譯。

### ATS 與文件結構

應徵者追蹤系統（ATS）能很好地解析 `.docx` 檔案——前提是文件很簡單。問題在
於，大多數 Word 履歷模板*並不*簡單：雙欄版面、表格、文字方塊、圖示與圖形，
正是這些元素會讓解析器混淆，而模板圖庫無法告訴您哪些設計是安全的。結果就
是一份在 Word 裡看起來很漂亮、卻在 ATS 中變成亂碼的履歷。

YAMLResume 的 DOCX 輸出是從結構化資料產生的，因此底層文件乾淨且可預測。
而當您需要可以可靠擷取的文字時，[Markdown 引擎](/zh-tw/docs/layouts/markdown)
會將同一份履歷輸出為純結構化文字，任何解析器——或 LLM——都能完美讀取。

## 生態系統

### 模板

Microsoft 的模板生態系統非常龐大：[Microsoft Create](https://create.microsoft.com/en-us/templates/resumes)
圖庫與無數的第三方網站提供數千個 Word 履歷模板，免費與付費皆有，涵蓋每一
種視覺風格。缺點是品質參差不齊——每個製作精良的模板背後，都有數十個使用
表格與文字方塊建立的模板，讓編輯變得困難，並讓 ATS 解析器失效。

YAMLResume 提供一小組精選模板：用於 DOCX 輸出的
[calm](/zh-tw/docs/layouts/docx/templates/calm) 模板，加上
[LaTeX](/zh-tw/docs/layouts/latex/templates) 與
[HTML](/zh-tw/docs/layouts/html/templates) 模板，全部針對每個支援的語系進行驗
證。因為模板是引擎設定而非文件，切換設計永遠不需要重寫內容。

### 招募人員與 `.docx` 格式

許多招募人員與申請系統會特別要求 Word 文件——某些 ATS 設定解析 `.docx` 的
可靠度高於 PDF，而且仲介機構經常在轉寄前移除您的聯絡方式，無論您喜不喜歡，
這都很常見。這正是 YAMLResume 內建 DOCX 引擎的原因。
[calm](/zh-tw/docs/layouts/docx/templates/calm) 模板會從相同的 YAML 原始碼產
生一份乾淨的 Word 文件，並提供與其他引擎相符的[頁面](/zh-tw/docs/layouts/docx#page)、
[排版](/zh-tw/docs/layouts/docx#typography)與進階選項（可點擊的 URL、聯絡方式
圖示）。

有一個注意事項適用於任何 DOCX 檔案，無論是否為產生的：字型必須存在於開啟
文件的機器上，否則 Word 會替換它們。請為您的 DOCX 版面配置選擇通用的字型，
並將 LaTeX/PDF 引擎作為完美外觀輸出的基準。

### 自動化

Word 有巨集；YAMLResume 有管線。[GitHub Action](https://github.com/yamlresume/action)
會在每次推送時建置所有格式，[Docker 映像檔](/zh-tw/docs/contributing/docker)
讓您無需本機設定就能在任何地方建置，而
[`@yamlresume/node`](/zh-tw/docs/ecosystem/node) 讓應用程式以程式設計方式讀
取、驗證並建置履歷。對於一年才更新一次的文件來說，這是小題大作；但對於一
份隨著職涯持續演進的動態履歷——以及需要大規模維護履歷的團隊——這會改變您
維護履歷的方式。

## 總結

**Microsoft Word** 適合以下需求：

- 到處都能使用的格式——每個招募人員都能開啟與編輯 `.docx`
- 零設定、無建置步驟的所見即所得編輯器
- 優秀的協作功能：即時共同編寫、註解、追蹤修訂
- 涵蓋每個產業與視覺風格的龐大模板圖庫
- 您已經擁有、並用於其他所有工作的熟悉工具

**YAMLResume** 適合以下需求：

- Git 中的單一純文字原始檔，具備真正的差異比對、歷史紀錄與分支
- 橫跨 [DOCX](/zh-tw/docs/layouts/docx)、[PDF](/zh-tw/docs/layouts/latex)、
  [HTML](/zh-tw/docs/layouts/html) 與 [Markdown](/zh-tw/docs/layouts/markdown)
  的自動產生且一致的格式設定
- 在招募人員發現之前就先攔下[結構錯誤](/zh-tw/docs/cli#validate)的[結構驗證](/zh-tw/docs/compiler/schema)
- 從單一真實來源出發的深度[國際化](/zh-tw/docs/locale)：[橫跨 10 種語言與 12 個語系代碼](/zh-tw/docs/locale)，並具備 [AI 翻譯](/zh-tw/docs/ai/translate)
- 設計上即確保 ATS 相容的輸出，外加適用於文字管線的 [Markdown 引擎](/zh-tw/docs/layouts/markdown)
- 自動化：[監看模式](/zh-tw/blog/dev-mode)、[CI/CD 建置](/zh-tw/docs/ecosystem/action)、[Docker](/zh-tw/docs/contributing/docker)，以及 [Node.js API](/zh-tw/docs/ecosystem/node)
- 透過[內建的 DOCX 引擎](/zh-tw/docs/layouts/docx)獲得 Word 相容性，*卻不需要* Word 的工作流程

如果您一年只寫一份履歷、與每天使用 Office 的非技術人員協作，或只是比起
結構更重視即時性，請選擇 **Microsoft Word**。

如果您的履歷是一份持續演進的文件——具備版本控制、為每份申請客製化、以多
種格式與語言發佈，並像您其他工作一樣以程式碼維護——請選擇 **YAMLResume**。
而當招募人員要求 Word 版本時，`yamlresume build` 會為您搞定一切。
