---
title: YAMLResume と Microsoft Word の比較
---

[Microsoft Word](https://www.microsoft.com/en-us/microsoft-365/word) は、世界の
ほとんどの人が履歴書を書くために使ってきたツールです。就職応募の既定のフォーマッ
トであり、何億台ものコンピューターにインストールされており、そのテンプレートギャ
ラリーは何千ものデザインを提供しています。採用担当者に「履歴書を送ってください」
と言われたら、10 回に 9 回は Word から書き出した `.docx` か PDF を期待されていま
す。

Microsoft 自身の製品ページからの引用です：

```markdown
- Word works across devices—on desktop (Windows and macOS), mobile, tablets
  (iOS and Android) or online.
- Word for the web is free for anyone to use online.
- Real-time collaboration means fewer email attachments and faster feedback.
```

重要なのはこういうことです。**YAMLResume を選ぶことは、Word 互換の出力を諦める
ことを意味しません。** YAMLResume には専用の [DOCX エンジン](/ja/docs/layouts/docx)
があり、1 つのコマンドで YAML ソースから Microsoft Word 文書をビルドします。本当
の比較は「YAML 対 `.docx`」ではなく、**手作業での文書編集 対 コンパイルされた構
造化された出力** です。この違いは、バージョン管理、検証、一貫性、マルチフォーマッ
ト公開、そして自動化に関わってきます。

2 つのワークフローの比較は以下の通りです：

## 機能比較

| 機能                       | YAMLResume                                                                                                          | Microsoft Word                                                                              |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **種類**                   | 履歴書コンパイラ（CLI ツールチェーン）                                                                              | 汎用ワープロソフト                                                                          |
| **作成形式**               | プレーンテキストの YAML                                                                                             | バイナリの `.docx`（XML の ZIP アーカイブ）                                                 |
| **フォーマット**           | テンプレートから生成されるため、フォーマットが一貫                                                                  | 手作業—スタイル、タブストップ、間隔が時間とともにずれていく                                 |
| **スキーマ検証**           | [厳格な Zod 検証](/ja/docs/compiler/schema) と [clang スタイルの診断](/ja/blog/yamlresume-compiler)                 | 構造に対する検証はなし—スペルと文法のみ                                                     |
| **出力形式**               | [DOCX](/ja/docs/layouts/docx)、[HTML](/ja/docs/layouts/html)、[Markdown](/ja/docs/layouts/markdown)、[LaTeX/PDF](/ja/docs/layouts/latex) | `.docx`、PDF（形式を選択して保存）、その他の形式への劣化したエクスポート                    |
| **DOCX 出力**              | 厳選されたテンプレートを備えた組み込みの [DOCX エンジン](/ja/docs/layouts/docx)                                     | 文書自体が DOCX                                                                             |
| **テンプレート**           | 厳選された公式セット（DOCX 用は `calm`、[LaTeX](/ja/docs/layouts/latex/templates) および [HTML](/ja/docs/layouts/html/templates) はさらに多数） | Microsoft Create やサードパーティ経由の何千ものテンプレート。品質は大きく異なる            |
| **バージョン管理**         | Git と連携。diff には実際の変更が表示される                                                                           | バイナリファイルのため、diff とマージは実質的に無意味                                       |
| **カスタマイズ**           | 応募ごとのレイアウトファイルと Git ブランチ                                                                           | 「名前を付けて保存」したコピーがどんどん乖離（`resume_final_v2.docx`）                      |
| **国際化**                 | [12 のロケールコードで 10 言語](/ja/docs/locale)、さらに [AI 翻訳](/ja/docs/ai/translate)                           | 多数の言語での UI とスペルチェック。各言語は別々の手作業の文書                              |
| **リッチテキスト**         | `summary` フィールドで一部の [Markdown 構文](/ja/docs/content/rich-text)                                            | あらゆる場所で完全なフォーマット                                                            |
| **データモデル**           | 固定された構造化スキーマ。[JSON Resume](/ja/docs/comparisons/json-resume) との相互運用                              | 自由形式の文書                                                                              |
| **AI 機能**                | CLI に組み込みの [生成](/ja/docs/ai/generate) と [翻訳](/ja/docs/ai/translate)                                      | Microsoft 365 Copilot 機能（サブスクリプション）                                            |
| **共同編集**               | プレーンテキストに対する Git プルリクエストとコードレビュー                                                         | 優れたリアルタイム共同編集、コメント、変更履歴                                              |
| **ATS 安全性**             | クリーンで生成された文書構造。テキストフィールドには [Markdown](/ja/docs/layouts/markdown) 出力                    | テンプレートの規律次第—表、テキストボックス、段組みは多くのパーサーを壊す                   |
| **決定論的出力**           | はい—同じ入力なら、どのマシンでも同じバイト                                                                           | フォントとレイアウトはマシンや Word のバージョン間で変わる                                  |
| **Dev モード**             | 保存するたびにリビルドする [`yamlresume dev`](/ja/blog/dev-mode)                                                    | WYSIWYG 編集（リアルタイムだが手作業）                                                      |
| **CI/CD と自動化**         | [GitHub Action](https://github.com/yamlresume/action)、[Docker](/ja/docs/contributing/docker)、[`@yamlresume/node`](/ja/docs/ecosystem/node) | 履歴書向けの組み込み機能はなし                                                              |
| **オフライン**             | はい（インストール後）                                                                                              | デスクトップアプリは可。Word for the web は接続が必要                                       |
| **コスト**                 | 無料（オープンソース）                                                                                              | Microsoft 365 サブスクリプション。制限付きの無料 Web 版                                     |

## 主な違いの解説

### 手作業のフォーマット 対 生成されるフォーマット

Word では、フォーマットはあなたの仕事です。箇条書きのインデント、日付のタブストッ
プ、太字の職名のひとつひとつが、あなたが決めて、決め直し続ける判断です。何ヶ月も
編集を重ねるうちに、文書はずれていきます。間隔が不揃いになり、新しい項目が微妙に
違う箇条書き記号を使い、「ちょっとした修正」に 20 分のあれこれ調整がかかるように
なります。調査によると、Word ユーザーの大多数は名前付きスタイルを使わないため、
フォーマットは結局、修正が苦痛な一回限りのインライン調整の集まりになってしまいま
す。

YAMLResume では、フォーマットはコンパイラの仕事です。コンテンツはデータであり、
[DOCX エンジン](/ja/docs/layouts/docx) と [LaTeX エンジン](/ja/docs/layouts/latex)
がテンプレートを通じてレンダリングし、一貫性を強制します。職名を 1 か所変更すれ
ば、DOCX、PDF、HTML、Markdown のすべての形式が次のビルドでそれを反映します。テ
ンプレートはデザイン判断を一度だけ行い、正しくやり遂げます。

### プレーンテキスト 対 バイナリ

`.docx` ファイルは XML で満たされた ZIP アーカイブです。Git が有用な diff を取る
ことはできず、履歴書の 2 つのバージョンをマージするには手作業でコピペする必要が
あり、「3 月と 6 月の間で何が変わった？」と聞かれれば、2 つのファイルを開いて横並
びで比較するしかありません。だからこそ、Word の履歴書は
`Resume.docx`、`Resume_new.docx`、`Resume_newer.docx`、`Resume_FINAL_tracked.docx`
という具合に、誰も整理する勇気のないフォルダーに積み上がっていくのです。

YAMLResume のファイルはプレーンテキストです。`git diff` が正確に何が変わったかを
示します：

```diff
-    position: Senior Software Engineer
+    position: Staff Software Engineer
     startDate: Jan 2020
-    endDate: Dec 2024
+    endDate:
```

プレーンテキストは、おなじみの開発者ツールを使えるようにします。応募ごとのブラン
チ、自分の職務経歴に対するプルリクエストレビュー、CI での自動ビルド、そして今ま
で作ったすべての履歴書の恒久的で検索可能なアーカイブです。

### 検証：スペルチェックは構造チェックではない

Word は雇用主名のスペルミスには波線を引きますが、終了日が開始日より前だったり、
メールアドレスに `@` がなかったり、都市名のフィールドが 1 文字だけだったりする履
歴書でも、保存はさせてしまいます。これらはどれもスペルミスではないので、どれも指
摘されません。

YAMLResume は、何かをレンダリングする前に構造を検証します。
[コンパイラ](/ja/docs/compiler/architecture) は履歴書を厳格な Zod スキーマに対して
チェックし、行番号とソーススニペット付きの
[clang スタイルの診断](/ja/blog/yamlresume-compiler) を報告するため、エラーは採用
担当者に気づかれるときではなく、書いている途中で捕捉されます。

### コピー地獄なしのカスタマイズ

キャリアのアドバイスは明確です。応募ごとに履歴書をカスタマイズすべきだと。Word
では、それは通常「名前を付けて保存」を選んでコピーを編集することを意味します。し
かしコピーはすぐに同期が外れます。1 つのファイルでタイポを直し、もう 1 つを忘れ
れば、今や 2 つの異なる履歴書があり、どちらが正しいか分からなくなります。

YAMLResume では、コンテンツファイルが唯一の信頼できる情報源であり続けます。カス
タマイズはレイアウト設定で行います。
[セクションエイリアスと並べ替え](/ja/docs/layouts/sections/aliases) はバリアントごと
に変更でき、Git がコンテンツの隣でそれらを追跡します。10 のカスタマイズされたバ
リアントとは、同じ履歴書を指す 10 の小さなレイアウトファイルであって、乖離してい
く 10 の個別の文書ではありません。

### 国際化、フェアに言えば

Word はこれが得意です。多言語文書、スペルチェック、中国語、日本語、韓国語を含む
複雑なスクリプトを非常に上手く扱い、英語圏以外の多くの国では履歴書の標準ツールで
す。1 つの言語で 1 つの履歴書を書くのであれば、Word の多言語サポートはあなたの問
題ではありません。

YAMLResume が輝くのは、1 つのキャリアが複数の言語を話さなければならないときで
す。`locale` キーを設定すると、セクションヘッダー、学位、スキルレベル、国名が翻
訳され、日付と住所がローカルなスタイルでフォーマットされ、
[10 言語 12 ロケールコード](/ja/docs/locale) にわたってロケールに適した句読点ルー
ルが適用されます。[`yamlresume ai translate`](/ja/docs/ai/translate) と組み合わ
せれば、英語から日本語へのバリアントも 1 つのコマンドで作れ、同じソースから生成
されるため 2 つが乖離することはありません。Word では、それは 2 つの文書と翻訳者
を意味します。

### ATS と文書構造

採用管理システム（ATS）は `.docx` ファイルを上手く解析します—文書がシンプルな場
合は。問題は、Word の履歴書テンプレートのほとんどがシンプルではないことです。2
段組みのレイアウト、表、テキストボックス、アイコン、グラフィックは、まさにパーサ
ーを混乱させるものであり、テンプレートギャラリーがどのデザインが安全かを教えては
くれません。その結果、Word では美しく見える履歴書が、ATS では文字の羅列になって
しまいます。

YAMLResume の DOCX 出力は構造化データから生成されるため、基盤となる文書はクリー
ンで予測可能です。そして確実に抽出できるテキストが必要なときは、
[Markdown エンジン](/ja/docs/layouts/markdown) が同じ履歴書を純粋な構造化テキスト
として出力するため、どんなパーサー—あるいは LLM—でも完璧に読み取れます。

## エコシステム

### テンプレート

Microsoft のテンプレートエコシステムは巨大です。
[Microsoft Create](https://create.microsoft.com/en-us/templates/resumes)
ギャラリーと無数のサードパーティサイトが、無料と有料、ありとあらゆるビジュアルス
タイルの Word 履歴書テンプレートを何千も提供しています。欠点は品質の不均一さで
す。質の高いテンプレートひとつあるごとに、編集を困難にし、ATS パーサーを壊す表
やテキストボックスで作られたものが何十もあります。

YAMLResume は小さな厳選セットを同梱します。DOCX 出力用の
[calm](/ja/docs/layouts/docx/templates/calm) テンプレート、プラス
[LaTeX](/ja/docs/layouts/latex/templates) と
[HTML](/ja/docs/layouts/html/templates) テンプレートで、すべてがサポートされてい
るすべてのロケールに対して検証済みです。テンプレートは文書ではなくエンジンの設
定であるため、デザインの切り替えがコンテンツの書き直しを意味することは決してあ
りません。

### 採用担当者と `.docx` フォーマット

採用担当者や応募システムの多くは、Word 文書を具体的に求めてきます。ATS の設定に
よっては `.docx` の方が PDF より確実に解析されることもあり、代理店が転送前に連
絡先情報を削除することがよくある—嫌がられても一般的に行われていることです。だ
からこそ YAMLResume には組み込みの DOCX エンジンがあるのです。
[calm](/ja/docs/layouts/docx/templates/calm) テンプレートは、同じ YAML ソースから
クリーンな Word 文書を生成し、[ページ](/ja/docs/layouts/docx#page)、
[タイポグラフィ](/ja/docs/layouts/docx#typography)、詳細オプション（クリッカブルな
URL、連絡先アイコン）は他のエンジンと揃えられています。

生成されるかどうかに関わらず、どの DOCX ファイルにも注意点が 1 つあります。フォ
ントは文書が開かれるマシンに存在している必要があり、なければ Word が代替フォン
トに置き換えます。DOCX レイアウトには普及したフォントを選び、完璧な見た目の出
力の参照として LaTeX/PDF エンジンを使い続けてください。

### 自動化

Word にはマクロがあります。YAMLResume にはパイプラインがあります。
[GitHub Action](https://github.com/yamlresume/action) はプッシュごとにすべての形式
をビルドし、[Docker イメージ](/ja/docs/contributing/docker) はローカル設定なしで
どこでもビルドでき、[`@yamlresume/node`](/ja/docs/ecosystem/node) はアプリケーショ
ンがプログラムで履歴書の読み取り、検証、ビルドを行えるようにします。1 年に 1 回
更新する文書であれば大げさです。キャリアとともに進化する生きた履歴書—そして大規
模に履歴書を保守するチーム—にとっては、履歴書の保守方法を変えるものです。

## まとめ

**Microsoft Word** は、以下を求める場合に優れています：

- どこでも動くフォーマット—採用担当者なら誰でも `.docx` を開き、編集できる
- セットアップもビルドステップもない WYSIWYG エディタ
- 優れた共同編集。リアルタイム共同編集、コメント、変更履
- あらゆる業界とビジュアルスタイルをカバーする巨大なテンプレートギャラリー
- すでに持っていて、他のすべての作業にも使っているおなじみのツール

**YAMLResume** は、以下を求める場合に優れています：

- Git に置かれた 1 つのプレーンテキストソースファイル。実際の diff、履歴、ブラン
  チ付き
- [DOCX](/ja/docs/layouts/docx)、[PDF](/ja/docs/layouts/latex)、
  [HTML](/ja/docs/layouts/html)、[Markdown](/ja/docs/layouts/markdown) にわたって一貫
  する生成されたフォーマット
- 採用担当者より先に[構造上のエラー](/ja/docs/cli#validate) を捕捉する
  [スキーマ検証](/ja/docs/compiler/schema)
- 深い[国際化](/ja/docs/locale)。単一の信頼できる情報源からの
  [10 言語 12 ロケールコード](/ja/docs/locale) と [AI 翻訳](/ja/docs/ai/translate)
- 設計上 ATS セーフな出力。プラス、テキストパイプライン向けの
  [Markdown エンジン](/ja/docs/layouts/markdown)
- 自動化。[ウォッチモード](/ja/blog/dev-mode)、[CI/CD
  ビルド](/ja/docs/ecosystem/action)、[Docker](/ja/docs/contributing/docker)、
  [Node.js API](/ja/docs/ecosystem/node)
- Word ワークフローなしの Word 互換。[組み込みの DOCX
  エンジン](/ja/docs/layouts/docx) による

年に 1 回履歴書を書き、Office で暮らす非技術者と共同作業するか、あるいは単に即
時性を構造よりも重んじるのであれば、**Microsoft Word** を選びましょう。

履歴書が生きた文書であり—バージョン管理され、応募ごとにカスタマイズされ、複数の
形式と言語で公開され、残りの仕事と同じようにコードとして保守されるのであれば、
**YAMLResume** を選びましょう。そして採用担当者に Word 版を求められたときは、
`yamlresume build` が対応します。
